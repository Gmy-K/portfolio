WORK 1

1: Claude Code Skills (automating study and posting)

In a nutshell: I keep building up instruction sheets (skills) that teach AI (Claude Code) "do this task with these steps", one for each purpose. When I ask, it works through the same steps every time.

Why I built it

  • Explaining the same thing to the AI every time is a hassle.
  • The result varies depending on how I phrase the request.
  • I forget to state the rules I want followed (don't rewrite things, don't look at the answer first, and so on) each time.

How it works

1. Ask

Example: "Write my reaction paper"

2. Pick a skill

The AI picks the skill that fits the request and reads it.

3. Carry it out

It works according to the "rules to follow" and the "steps".

4. Result

Notes, text, suggestions and so on.

What is inside a skill

One skill is one folder. Inside is a single instruction sheet (a Markdown file, SKILL.md). At the top it says "when to use this, depending on how I'm asked", and the body holds the "rules to follow" and the "steps".

What they can do

List of what the skills can do
AreaWhat it can do
Lectures and examsTranscribe lecture slides (PDF) into notes / write a reaction paper from lecture notes / draft answers to exam questions using the lecture notes as the source
English vocabularyDigitise handwritten English vocabulary cards and turn them into searchable notes
Tasks and reviewRegister, break down and complete tasks / turn weekly routines into tasks / create review questions and do daily review
Daily checkToday's briefing / updating the web dashboard
Posting and videoDrafting study-abroad Note articles / suggesting VOICEVOX voice tuning

I made 14 skills to support university study. There is also one more skill, for planning events for my club.

Things I put thought into

  • Write the "rules to follow" first.For example: in review, don't show the correct answer first. Don't rewrite the user's reasons. When completing tasks, tick only the ones that were named.
  • Keep the scope narrow.For example, for vocabulary cards I split "turning it into text" and "turning it into notes" into separate skills.
  • Keep the reasons.Each time I build one, I record why I did it that way in a design record (ADR).
  • Easy to fix.If I want to change the steps, I just edit the instruction sheet and the change applies everywhere from next time.

How I built it

  1. Design
  2. Write the instruction sheet
  3. Try it by actually asking
  4. Add failure cases to the sheet

They are version-controlled in a repository that gathers my configuration files. There are 5 design records for the skills.

WORK 2

2: VOICEVOX Voice-Tuning Skill (suggesting tuning parameters from a line)

In a nutshell: Tell it a line, a character name and a tone (for example, deadpan and surreal), and it suggests recommended values for VOICEVOX's tuning parameters (speed, pitch, intonation, volume, pauses and silence). I use it when making the narration for my study-abroad vlog.

Problems I wanted to solve

  • For a Reel's narration, I tune many lines, each in a slightly different tone.
  • Deciding the numbers by trial and error every time was hard.

How it works

Input

  • The text of the line
  • Character name
  • A description of the tone (in free-form text)

Pick a preset

Choose the one of five closest to the tone.

  • Deadpan / surreal
  • High-energy / fast-talking
  • Expressive / friendly
  • Calm narration
  • Other

Fine-tune

Scan the text of the line and adjust the numbers.

  • For 40 characters or more, raise the speed a little
  • If there is an "!", raise the intonation
  • If there are many commas, lengthen the pauses
  • For a punchline under 10 characters, add silence before and after

Output

Returned as a table. The order matches the parameters on the VOICEVOX screen, so I can copy the values straight onto the sliders while looking at it.

Things I put thought into

  • The numbers are a "starting point".Every time, it notes that they are not measured values.
  • Some things are not turned into numbers.For the intonation of questions and the accent of proper nouns, it notes "check manually".
  • No invented numbers.Where something is written only in words (for example, "normal to slightly long"), no number is attached.
  • It doesn't make audio.It does not generate the audio itself. I apply the values by hand on the VOICEVOX screen.

Design choice

I compared three approaches.

  • (A) A fixed table only
  • (B) Build values with rules for each line
  • (C) Use a table as the base and fine-tune with rules

I chose (C), which balances stability with the individuality of each line (design record ADR 008).

How I built it

I did the design first and then wrote the instruction sheet. The presets and the fine-tuning rules are written statically in the sheet.

WORK 3

3: Study-Abroad Budget Book (logging spending and showing budget pace)

In a nutshell: A web app for my own use that lets me record spending while studying abroad in a few seconds from my phone, and see my pace against this month's budget.

Problems I wanted to solve

  • Cashless payment (tapping a card) is the norm, so there are many small payments in a day.
  • If entering things is a hassle, I won't keep it up.

How it works (three components)

Screen

Built with HTML and JavaScript. Charts use Chart.js.

Calculation

A file that gathers only pure functions. It is separated from the screen and the data, so it can be tested with Node.js.

Data

A small database in the cloud. The same data can be used from my phone or my computer. It is for personal use, so there is no login.

I built it as a Claude Artifact (a place to host small web apps). Bookmarking a single URL is enough to use it.

What the screen can do

  • Record spending quickly.
  • Compare this month's spending with the budget (with a marker for the daily pro-rated pace).
  • A chart of daily spending.
  • An outlook for the balance.
  • The flow of money, split into fixed and variable costs.
  • Automatic adjustment of the food budget according to the number of meals, for housing that includes meals.
  • Management of money-transfer plans.

Things I put thought into

  • Keep the effort of entering data as small as possible.This is the most important constraint in the design.
  • Separated the calculation from the screen and wrote tests.
  • Design first.For each feature, I wrote a design document and an implementation plan before building it.
  • Recorded decisions in design records (ADR).There are four.
    • Holiday and meal-count data are constants in the calculation file.
    • The food budget for holiday months is increased automatically by the ratio of meal counts, and reflected only in the display.
    • Transfer settings are kept in a separate data document.
    • The monthly change in assets is calculated from the records.

How I built it

For each feature I repeated "design document → implementation plan → test-first implementation".

Tech notes

  • JavaScript
  • Chart.js
  • Claude Artifact (database feature)
  • Node.js (tests)
  • Design records (4 ADRs)
